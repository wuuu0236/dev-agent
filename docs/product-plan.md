## 1. 产品定位

### 1.1 一句话

> **DataLens 是一个跑在自己电脑上的私有知识库问答系统：把散落的 PDF / Word / 扫描件 / 笔记变成能对话的库，答案带可核实的原文出处，且敢说"我这里没有"。**

拆开看，这句话里每个词都是刻意的：

| 措辞 | 对应的事实 | 为什么必须强调 |
|---|---|---|
| **跑在自己电脑上** | 推理后端可全切 Ollama，数据不出本机 | 这是唯一一条大厂产品给不了的价值 |
| **散落的 PDF / Word / 扫描件 / 笔记** | 输入是**已有的文档**，不是重新录入 | 不是"知识管理工具"，是"知识消费工具" |
| **能对话** | 多轮追问、追问消解 | 检索式搜索和对话式检索是两种体验 |
| **可核实的原文出处** | 引用给到命中原文片段，不只是文件名 | 不可核实的引用等于没有引用 |
| **敢说"我这里没有"** | 质量门控，分数不够就不生成 | 通用模型没有"你的库里没有"这个概念 |

### 1.2 目标用户

**主用户（真实使用者）：有本地文档堆积、且在意数据不出本机的人。**

具体画像：

- 手里有几百份 PDF / 论文 / 技术文档 / 会议记录，散在文件夹里
- 遇到过"我记得看过这个，但翻不到了"
- 对把内部文档传给第三方 API 有顾虑（工作文档、未发表内容、客户资料）
- 有基本的动手能力（能装 Python、跑命令），不需要图形化安装包

> ⚠️ **不把"不懂技术的普通用户"当目标用户。** 本地部署这件事本身就筛掉了他们，
> 为他们做设计（一键安装包、引导式 UI）会让产品失去焦点。要服务的是
> **"愿意为了数据私有付一点部署成本"的人**。

**次用户（评审者）：面试官 / 技术同行。**

这个必须诚实写出来 —— 它影响很多设计取舍：

- 他们的使用时长是 **3-5 分钟**，不会上传自己的文档
- 他们要判断的是"这个人懂不懂工程"，不是"这个工具好不好用"
- 对应设计：**冷启动自动预置演示知识库**（`scripts/seed.py`），打开就能问；
  README 把每个技术决策的**数据依据**写进去（0.960→1.000 这种）

→ **两类用户的需求在这一处冲突**：真实使用者嫌"演示库"占地方，评审者需要它。
当前解法：预置但可删（`app.py` 冷启动幂等补建），不强制。

### 1.3 使用场景

不是"每天打开 20 次"的高频工具，而是**低频但高价值**：

| 场景 | 频次 | 触发点 |
|---|---|---|
| 查自己文档里的某个细节 | 每周几次 | "我记得写过 / 看过，但找不到" |
| 读新论文 / 新文档时对着问 | 不定期 | 文档长、想跳过通读直接问 |
| 整理某主题时横向找 | 偶尔 | "我关于 X 的资料里都提了什么" |
| 面试 / 汇报前快速回顾 | 里程碑 | "我之前那个项目的关键数字是多少" |

> **这个频次判断很重要**：它直接否决了一整类设计。
> 低频工具不需要"每日打卡""使用时长""连续登录"这类留存设计，
> 它需要的是**想起来用的时候，5 分钟内能拿到可信答案**。
> 所以产品优化的方向是「单次使用的成功率」，不是「使用频次」。

### 1.4 价值主张

**给主用户**：你的文档不用出本机，问出来的答案有原文可查，不知道就直说 —— 这三点，通用聊天工具一条都做不到。

**给次用户（评审者）**：这个项目的每一个设计决策，都有实测数据支撑，包括**被否决的方案**。

## 2. 为什么需要它 —— 与替代方案的真实对比

### 2.1 替代方案清单

| 替代方案 | 它的优势 | 它的短板 |
|---|---|---|
| **直接问 ChatGPT / DeepSeek** | 零成本上手、能力强、什么都能聊 | 不知道你的文档；会自信地编；不能核实 |
| **手动 grep / 文件搜索** | 精确、可核实、零依赖 | 只能匹配字面；换个说法就搜不到 |
| **企业级平台（Dify / MaxKB / FastGPT / RAGFlow）** | 功能成熟、有 UI、能多人协作 | 要部署服务、面向团队、数据在自己服务器上仍非本地 |
| **把文档贴进对话窗口** | 简单直接 | 上下文长度限制；只适合单次少量 |
| **什么都不做** | 省事 | 继续"记得看过但找不到" |

### 2.2 「为什么不直接问 ChatGPT」—— 正面回答

这是这个产品必须答上的第一问。答案不是"我更准"（**在小语料上这句话站不住**），而是三个**结构性**差异：

| 差异 | 为什么通用模型做不到 | 本项目的实现 |
|---|---|---|
| **① 它不知道你的文档** | 模型权重里没有你的私有内容，除非你贴给它 | 本地索引 + 检索，问什么搜什么 |
| **② 它会自信地编** | 没有"我的知识边界在哪"这个信号，被问到时只能生成 | **质量门控**：精排最高分低于阈值就**不把上下文交给模型**，改用无依据提示词如实说没有（`src/answer_gate.py`） |
| **③ 你说不出它哪句是编的** | 输出是自由文本，没有落到具体来源 | **引用三层**：模型只准给序号 `[n]` → 代码映射回真实检索块 → 给出**命中原文片段**（`src/citations.py`） |

第 ② 条是最硬的。实测数据（2026-09-14）：

```
可答问题 top1 精排分  0.62
闲聊问题             0.125
常识问题             0.091
越界问题             0.010
```

**可答与不可答之间差 5 倍**，一个阈值就分得开。所以 DataLens 能在"我这没有"的时候真的说没有 —— 而通用模型没有"我这"这个概念。

> 第 ③ 条常被误解成"有没有引用功能"。区别在于**引用可信到什么程度**：
> 只给文件名 → 用户无法核实，只能选择相信
> 给到原文片段 → 用户展开就能自己判断（`pages/3` 里引用可展开）
> 前者是装饰，后者才是可核实。

### 2.3 与企业级平台的对比（诚实版）

**结论：正面竞争打不过，也不该打。**

| | Dify / MaxKB / FastGPT | DataLens |
|---|---|---|
| 目标 | 团队 / 企业知识中台 | 个人本地知识库 |
| 部署 | 服务端，多人访问 | 本机，单人使用 |
| 文档量级 | 万级 / 十万级 | 百级 ~ 千级 chunk |
| 数据边界 | 自己的服务器 | **本方电脑，可完全离线** |
| 成熟度 | 生产验证过 | 个人项目 |
| 独特能力 | 工作流编排、插件生态、权限体系 | **每个决策可追溯到 A/B 数据** |

诚实地说，论功能完备度这个项目差得远。所以它的位置**不是"更小的 Dify"**，而是：
**"一个数据不出本机、且工程过程完全透明可查的个人工具"**。

> ⚠️ **绝不宣称"企业级"。** 企业级要的是多租户、权限、SLA、审计，
> 这些一个都没有（`notes/enterprise-refactor-plan.md` 里已列明差距）。
> 硬套这个词，面试官问三个问题就会穿帮。**诚实的定位反而更难被击穿。**

## 3. 产品边界

### 3.1 做什么

| 维度 | 边界 |
|---|---|
| **输入** | 用户已有的文档：PDF、Word、Markdown、TXT、CSV、图片（OCR）、扫描版 PDF |
| **输出** | 带原文出处的自然语言回答；检索不到时明确说没有 |
| **形态** | 本地 Web 界面（Streamlit）+ HTTP API + MCP 工具（给 AI 客户端用） |
| **规模** | 单知识库百级 ~ 千级 chunk；多知识库并行（SQLite 元数据 + Chroma 向量） |
| **部署** | 本机运行；可完全离线（Ollama 后端） |

### 3.2 明确不做（非目标）

**这一节比"做什么"更重要 —— 它保护产品不被无限摊薄。**

| 不做 | 理由 |
|---|---|
| ❌ 多租户 / 权限 / 账号体系 | 单机单用户，引入认证是纯复杂度。企业级能力不是这个产品的战场 |
| ❌ 团队协作 / 分享链接 | 定位是私有，分享从根上矛盾 |
| ❌ 文档在线编辑 / 知识库富文本管理 | 这是另一类产品（Notion / 语雀）。本产品的输入是**已有的**文档 |
| ❌ 自主规划型 Agent（多步任务、自动调工具链） | 问答要的是**快和可核实**。把 RAG 塞进 ReAct 循环只会让问答变慢、引用变难（这就是双入口分工的由来） |
| ❌ 自动调参 / 自动优化 | 语料规模不足以支撑统计显著性，自动优化 = 过拟合到噪声 |
| ❌ 模型微调 | 标注量差几个数量级，且 RAG 链路不需要 |
| ❌ 多模态生成（画图 / 做 PPT） | 本产品的输出是"文档里的答案"，不是"新内容" |
| ❌ 吸引非技术用户的一键安装包 | 会稀释产品焦点（见 §1.2 的取舍） |

## 4. 功能版图（按用户旅程组织）

> 为什么不按技术模块（解析 / 检索 / 生成）组织：那是**实现视角**，看不到用户在哪一步掉队。
> 按旅程组织才暴露得出"哪个阶段是空的"—— 下面的「阶段三」就是这么被找出来的。

### 阶段一：上手 —— 「我 5 分钟内能不能问出第一个答案？」

| 能力 | 状态 | 说明 |
|---|---|---|
| 冷启动自动预置演示库 | ✅ | `scripts/seed.py` 幂等，打开就能问，不用先上传 |
| 上传文档 | ✅ | 拖拽上传，多格式（PDF/docx/md/txt/csv/图片） |
| 解析进度与状态反馈 | ✅ | **比预期扎实**：`st.progress` 进度条 + 分阶段文案（解析 → 切块 → 向量化），大文件不黑屏 |
| 报错分类 | ✅ | 分四类如实报告：超限 / 无可提取文本 / 内容太短 / 处理失败，并落库为 `error` / `empty` 状态 |
| 空库引导 | ✅ | 「请先在知识库管理中创建知识库」 |
| **新用户不知道该问什么** | ❌ | **无推荐问题 / 示例问法**。演示库预置好了，但用户面对空输入框不知道从哪问起 |

**缺口**：上传路径的反馈做得不错 —— 这一点我原先低估了，实测有进度条和四类错误提示。

真正的缺口在**第一个问题的引导**：演示库预置了内容，却没有任何"你可以试试问这些"的入口。
用户要么随便问一句（很可能正好问到库里没有的），要么直接关掉。**而第一次就撞上"未命中"，
会形成"这工具没用"的第一印象** —— 这个首因效应的代价，远大于多写几行引导文案的成本。

> 这也修正了我对阶段一的初始判断：问题不在"反馈不足"，在**"第一次成功的概率不够高"**。

### 阶段二：日常问答 —— 「答案可不可信？」

| 能力 | 状态 | 说明 |
|---|---|---|
| 多轮追问 | ✅ | 最近 6 轮历史注入 |
| 追问消解 | ✅ | 「那第二点呢」→ 自包含 query（`src/query_rewrite.py`） |
| 混合检索（向量 + BM25 + RRF） | ✅ | 两路同开，互补（专有名词靠 BM25） |
| 交叉编码精排 | ✅ | 池 50 → top 5，实测 MRR 0.887→0.960 |
| 质量门控（敢说不知道） | ✅ | 分数不够不喂上下文（`src/answer_gate.py`） |
| 引用可核实 | ✅ | 展开看命中原文（`src/citations.py`） |
| 流式输出 | ✅ | 真流式（按 token） |
| 语义缓存 | ✅ | 换说法也能命中，重复问题秒回 |
| **显示"为什么没命中"** | ❌ | 只说"未命中知识库"，**不告诉用户分数是多少**。0.28（差一点）和 0.02（真没有）对用户意味着完全不同的下一步 |
| **答案质量反馈入口** | ❌ | 答得对不对，用户没有任何表达途径（见 `notes/feedback-loop-plan.md`） |

**缺口**：答案的可信度**链路**已经很完整，但用户**感知**不到。用户看到"未命中"时不知道是自己问法问题、文档没传、还是真没有。

### 阶段三：知识积累 —— 「用了一个月，它有没有变强？」

**🔴 这是产品最空的一段，也是本方案最重要的发现。**

| 能力 | 状态 |
|---|---|
| 问答历史记录 | ❌ 刷新即失（只存在 `st.session_state`） |
| 收藏 / 标记有价值问答 | ❌ |
| 从问答中发现知识库缺口 | ❌ |
| 知识库随时间演进的可视化 | ❌ |

**问题**：现在的产品**每一次使用都是孤立的**。用完一个月，除了文档多了几份，系统对"你常问什么、什么答不上来"一无所知。

→ 这一段空着，产品就是**工具**；补上，才是**系统**。

### 阶段四：出问题时 —— 「答错了，我能不能查出来为什么？」

| 能力 | 状态 | 说明 |
|---|---|---|
| 引用可展开看原文 | ✅ | 用户侧能自己核对 |
| **当次问答的现场快照** | ❌ | 看不到当时检索到了什么、分数多少、门控有没有拦 |
| 文档删干净（无幽灵引用） | ✅ | Chroma + SQLite + 原文三处同删 |
| 内容级 bug 自查 | ⚠️ | docx 表格已修；PDF 表格结构仍错乱（已知问题，需版面分析） |

**缺口**：用户（和开发者）都**无法复盘**。用户觉得答错了，只能重新问一遍；开发者想查，只能去复现，而"上周那次检索到了什么"根本查不到。

### 阶段五：持续变好 —— 「配置改了，老库跟不跟得上？」

| 能力 | 状态 | 说明 |
|---|---|---|
| 原文留存 | ✅ | `data/uploads/{kb_id}/`，按库分目录 |
| 索引可重建 | ✅ | 管理页一键「重建索引」（`src/reindex.py`） |
| 检索质量评估 | ✅ | Recall@K / Hit@K / Hit@1 / MRR + 历史存档对比 |
| 生成质量评估（RAGAS） | ✅ | 四维百分制 + 多配置对比 |
| 可观测性（Langfuse） | ✅ | trace / token / 延迟 |
| 反馈回流 | ❌ | 见 `notes/feedback-loop-plan.md` |

**这一段是全项目最成熟的部分**（可能是最成熟的个人 RAG 项目之一）。但缺最后一环：**上面的所有能力，目前只有开发者（我）会主动去看，用户没有任何输入通道。**

## 5. 核心用户旅程

### 5.1 新用户 5 分钟

```
打开 Demo 链接
   │
   ├─→ 看到预置的「DataLens 演示」知识库（无需上传）      ← 阶段一 ✅
   │
   ├─→ ⚠️ 面对空输入框，不知道问什么（无推荐问题）
   │      └─→ 随便问一句 —— 有相当概率问到库外
   │             └─→ 第一次体验就是「未命中」             ← ❌ 首因效应最差的情形
   │
   ├─→ （若问对了）流式答案出现 + 引用来源
   │      └─→ 展开引用，看到命中原文                      ← 阶段二 ✅
   │
   └─→ （若问库外）"知识库中没有找到相关内容"              ← 阶段二 ✅
          └─→ ⚠️ 但不知道分数，也不知道是自己问错了还是真没有
```

**设计目标**：让用户在 5 分钟内同时体验到「答得准」和「敢说不知道」这两件事。

**但当前路径保证不了这件事** —— 因为它把"第一个问题"完全交给了运气。改进只需一步：
**预置几个演示问题，其中刻意包含一个库外问题**，让两件事都被用户主动看到，
而不是碰运气撞上。

> 注意这里的目标不是"让用户看到产品功能多"，而是**让用户在 5 分钟内理解这个产品的性格**：
> 答得准 + 不知道就直说。后者是差异点，必须被主动展示，不能等用户撞。

### 5.2 老用户日常

```
有一个具体问题（读论文中途 / 写东西需要引用 / 汇报前回顾）
   │
   ├─→ 打开 → 选知识库 → 提问
   │
   ├─→ 答案满意 → 关掉
   │      └─→ ❌ 无历史记录，下次想问同一个得重新组织问题    ← 阶段三
   │
   └─→ 答案不对/没有
          ├─→ 换个问法再问（可能问对，也可能放弃）
          └─→ ❌ 这个"答不上来"的信号没有被记录            ← 阶段三/四
```

**这里暴露的问题**：老用户的**每次使用都是冷启动**。产品没有从历史使用中学到任何东西。

### 5.3 关键结论

| 阶段 | 成熟度 | 判断 |
|---|---|---|
| 一 上手 | 🟡 上传扎实、**首问无引导** | 短板是"第一次成功的概率"，不是反馈不足 |
| 二 日常问答 | 🟢 强 | 链路完整，但"可信度"没被用户感知到 |
| 三 知识积累 | 🔴 **空** | **最大结构性缺口** |
| 四 出问题 | 🟡 半 | 用户侧能核实，开发者侧不能复盘 |
| 五 持续变好 | 🟢 强 | 只差反馈回流 |

→ **产品现在的形态是「一次性问答工具」，不是「越用越好的系统」。**
差距不在检索算法，在阶段三。

## 6. 关键产品决策与取舍

> 每个决策都记录**代价**。只讲好处不叫设计，叫宣传。

| # | 决策 | 为什么 | 代价 | 可复用原则 |
|:--:|---|---|---|---|
| 1 | **双入口分工**：Web 走确定性 RAG，API 走 LangGraph 工具循环 | 问答要快、引用要准；文件操作要灵活。两种需求塞进一个循环会互相拖累 | 两套实现要维护 | 按**任务性质**分路径，不按"技术先进性"分 |
| 2 | **RAG 不放进 ReAct 循环** | 塞进去会让问答变慢、引用变难 | 失去"Agent 自动决定查不查库"的灵活性 | 确定性流程就不要用自主决策去跑 |
| 3 | **敢说"不知道"**（门控） | 防幻觉最直接的一道闸；拒答 ≠ 拒绝服务 | 阈值定不好会误杀（0.3 是保守初值，负样本仅 2 条） | 宁可少答，不可错答 —— 但**不能阻断问答** |
| 4 | **引用给到原文** | 只给文件名 = 用户无法核实 = 引用是装饰 | 界面变长，存储 snippets | 可核实性 > 界面简洁 |
| 5 | **失败一律降级，不报错** | 精排失败退回粗排顺序、改写失败退回原 query、缓存失败照常回答 | 用户不知道"这次是降级跑出来的" | 优化环节允许失效，**绝不能阻断主流程** |
| 6 | **配置全开关化 + 可 A/B** | 每个改动都能被验证，也能被否决 | 配置项变多 | 没有开关的优化无法证伪 |
| 7 | **上传保留原文** | 索引被冻在入库参数上，没原文就永远无法重跑 | 占磁盘 | 可重建性依赖原始输入 |
| 8 | **重建逐文档替换** | 单文档失败不连累其他；缺原文不动旧索引 | 比整库清空慢 | 批量操作要逐项隔离，失败 = 什么都没发生 |
| 9 | **RRF 融合 + 精排分数做阈值**（两条一起用） | 见下方专项说明 —— 这是本项目的关键设计判断 | RRF 分数本身无绝对意义，不能直接做阈值 | 融合策略和判决策略可以分工 |
| 10 | **参数必须能被证伪**（每个改动都有 A/B） | 见 §6.2 | 开发慢 | 工程透明本身就是产品差异 |

### 6.1 专项：RRF 与阈值的关系（一个被解决的问题）

`notes/maxkb-benchmark.md` 里记录过一个真实的两难：

> RRF 的好处是不需要关心两路分数的量纲，但代价是**丢掉了绝对分数信息** —— 而绝对分数正是阈值过滤的基础。
> **所以：加阈值和用 RRF 是冲突的。**

MaxKB 的解法是放弃 RRF，改成分数相加融合（让分数可解释）。

**本项目的解法不同，而且更干净**：RRF 保留，但**不用 RRF 分数做阈值 —— 用交叉编码的精排分数**。

- **RRF 负责召回**：不需要调参、不需要归一化，两路分数量纲无关
- **精排分数负责判断**：交叉编码输出的是"query 与文档片段的相关性"，有绝对意义（相关 0.6+ / 不相关 <0.01）

→ **融合策略和判决策略是两个独立的问题，可以分开选。** 不必为了能用阈值就换掉融合算法。

这个判断的价值在于：它避免了"为了一个功能去重构另一个模块"的连锁改动。

### 6.2 专项：工程透明度作为产品差异

README 里很多表述是**别的项目不会写的**：

| 常见写法 | 本项目的写法 |
|---|---|
| "支持混合检索" | "混合检索已开启；但本测试集上四项指标**完全相同**，价值在能力覆盖而非分数" |
| "使用 rerank 提升效果" | "Recall@5 0.960→1.000、MRR 0.887→0.960（同库同测试集，只切一个开关）" |
| "支持多种分块策略" | "标题树分块在 md 语料上**实测负优化**（MRR 0.887→0.873），战场在 PDF/Word，已回退但保留代码" |
| "已开启 BGE 查询指令" | "实测 top1 相似度 **0.6170→0.5554**，客户端加前缀有害（服务端已处理），默认关闭" |

**为什么这是产品差异而不是"过度分享"**：目标用户是技术人。对他们来说，**"这个项目会诚实地告诉我什么没用"比"这个项目功能多"更有说服力** —— 因为它意味着剩下的功能是真的有效的。

### 6.3 一条被验证的方法论

项目里出现过两次同样的失败模式，值得固化：

> **最佳实践必须放回自己场景重测。**
> - MaxKB 的标题树分块 → 在 md 语料上负优化
> - BGE 官方推荐的查询指令前缀 → 在硅基流动上因为服务端已处理而有害

以及一条：

> **改任何东西之前先验证尺子。**
> - 曾在 18 chunk 的小库上做 A/B，Recall@5 恒为 1.0 —— 尺子饱和，所有结论都是幻觉
> - 曾量到"精排分数 +2.6%"，验证后发现精排分数有 ±0.01 抖动，该结论落在噪声内，作废

## 7. 竞品格局与定位空隙

### 7.1 四类玩家

| 类型 | 代表 | 强项 | 弱点 |
|---|---|---|---|
| **通用对话模型** | ChatGPT / DeepSeek | 零门槛、能力全面 | 不知道你的文档；会编；不可核实 |
| **企业知识平台** | Dify / MaxKB / FastGPT / RAGFlow | 功能完备、多人协作、生产验证 | 部署成本高、面向团队、数据在服务器上 |
| **本地优先工具** | AnythingLLM / GPT4All / Cherry Studio | 一键装、体验好、离线 | 检索链路黑盒，无评估体系，不可验证 |
| **手写 RAG 项目** | GitHub 上的大量教程项目 | 轻 | 通常停在"跑通"，无评估、无 A/B、无运维 |

### 7.2 空隙在哪

```
             功能完备度 高
                  │
   企业平台 ●      │      ● 本地优先工具
  (Dify/MaxKB)    │     (AnythingLLM)
                  │
 ─────────────────┼─────────────────→ 数据私有性 高
                  │
   教程项目 ●      │      ◆ ← 空隙
                  │        「私有 + 可验证」
                  │
             功能完备度 低
```

**空隙 = 「数据完全私有」×「每个决策都可验证」**：

- 企业平台够强，但数据在服务器上、且你无法知道它的检索到底怎么调的
- 本地工具够私有，但检索链路是黑盒，出问题无法归因，也无法自己改进
- 教程项目两边都不占

DataLens 站在这个位置上。**它的卖点不是"我功能多"，而是"我知道我每个功能的真实效果，包括没用的那些"。**

> ⚠️ 这个定位有个现实约束：**它吸引的是会看代码的人**。这正好和目标用户（§1.2）重合 ——
> 但意味着产品**不需要**为"看不懂 README 的人"做优化。

## 9. 演进路线

> 排序依据：**先补结构性缺口，再做锦上添花**。不按技术难度排。

### V1 —— 已完成（当前）

确定性 RAG 全链路 + 双入口 + 评估体系 + 索引运维 + 可观测。

**V1 的核心成就**：链路完整且**每一步都有数据支撑**。

### V2 —— 补上"积累"与"反馈"（当前建议）

| 优先 | 事项 | 为什么排这里 |
|:---:|---|---|
| 1 | **预置演示问题（含一个库外问题）** | **改动最小、直击首因效应**。现在第一个问题靠运气，撞到"未命中"就废了。几行文案就能把"敢说不知道"变成主动展示 |
| 2 | **"为什么没命中"提示**（把 `gate_score` 露给用户） | 同样是**一行改动**，直接补上阶段二那个"感知不到可信度"的缺口。0.28 和 0.02 对用户意味着完全不同的下一步 |
| 3 | **P0 问答黑匣子**（`answer_log`） | 阶段三/四共同的底座。没有它，反馈无法归因、缺口无从发现。**且它不依赖用户点任何按钮**——`grounded=0` 的记录天然就是"知识库缺口清单" |
| 4 | **P1 反馈入口**（👍/👎 + 备注） | 有了黑匣子，反馈才有意义；`pages/3` 目前全文只有 1 个按钮 |
| 5 | **P2 三档回流** | 接到已存在的出口上（缓存作废 / 补文档重建 / 沉淀评测集），不新建机制 |
| 6 | 问答历史（可回看、可收藏） | 解决老用户每次冷启动的问题 |

> 1-2 是**产品方案与环节方案的排序差异**：`feedback-loop-plan.md` 从"环"的角度排，
> 黑匣子排第一（因为它是反馈环的地基）。这里从"用户能不能留下来"的角度排，
> 前两项成本几乎为零但直接决定首因效应 —— **先用最小代价把门开着**，再建底座。
> 两者不冲突，只是同一条路的不同走法。

> 3-5 见 `notes/feedback-loop-plan.md`（已有完整设计）。
> **1-2 是这份产品方案独有的判断**：它们的成本几乎为零（文案 + 一行分数显示），
> 但直接决定"第一次用会不会留下"和"用户知不知道该信到什么程度"。
> 大功能值得做，但**先把门开着**。

### V3 —— 稳健性与工程化

- API 认证 + 限流（当前 `/chat` 无认证，可读文件 + 烧 token）
- 统一错误处理 + request_id
- 部署完整性（compose 含 Web、去掉本机路径挂载）
- 测试覆盖主链路（现有测试偏"新写的模块"，主链路覆盖不足）
- 内容 hash 去重 / chunk id 唯一化

> 详见 `notes/enterprise-refactor-plan.md`。**排在 V2 之后**：这些是"企业级叙事"要的，
> 而 V2 是"产品能不能站住"要的。当前阶段的用户是单机单用户，认证的紧迫性低于积累能力。

### V4 —— 检索质量深化（按需）

- 关联问题生成（MaxKB 的召回杀手锏，性价比高，纯增量）
- 高相似直接返回（省 LLM 调用 + 零幻觉）
- PDF 表格版面分析（**独立课题**，需坐标级行列聚类，量级明显更大）
- 查询扩展 / HyDE / 多跳分解

### 长期探索

- 会话级需求归并（问 A 答 B、换问法重问 → 识别为同一需求）
- 知识库版本化（文档变更历史 + 影响范围）

## 10. 怎么衡量产品在变好

**不能用"检索指标"当产品指标** —— 它会诱导优化没人问的题目。

| 层 | 指标 | 现状 |
|---|---|---|
| **产品层**（最终） | 「想查一个东西 → 拿到可信答案」的**单次成功率** | 无度量 |
| **感知层** | 未命中率、用户改问率、反馈满意率 | 无度量（反馈环未建） |
| **能力层** | Recall@K / Hit@K / MRR / RAGAS 四维 | ✅ 已有 |
| **成本层** | 缓存命中率、平均延迟、token 消耗 | 部分有（Langfuse） |

> **三层的关系**：能力层是手段，感知层是证据，产品层是目的。
> 现在只有能力层和部分成本层 —— 这正是"**感知层缺失**"的具体含义。

**近期最该补的度量**（都在 P0 黑匣子里）：未命中率、`gate_score` 分布、缓存命中率。有了这三个数，"产品在变好"才有依据。

## 11. 风险与挑战

| 风险 | 影响 | 对策 |
|---|---|---|
| **首问撞空**：新用户第一个问题就问到库外 | 首因效应 → 用一次就走 | 预置演示问题（**含一个刻意的库外问题**），把"敢说不知道"从碰运气变成主动展示 |
| **低频使用**：想不起来用 | 留存低 | 接受它 —— 低频工具不需要留存设计，优化单次成功率 |
| **可信度靠用户读 README** | 价值传达不到 | Demo 里**体验化**：未命中时显示分数、引用默认可展开 |
| **PDF 表格结构错乱** | 隐性信息损失 | 已知问题已写进 README（诚实标注）；修复列为独立课题 |
| **单点：所有能力都依赖 LLM API** | 断网/欠费即不可用 | 已支持 Ollama 全离线（差异化能力，不是兜底） |
| **没有反馈就无法自我改进** | 停在工具形态 | V2 首位（黑匣子） |
| **定位漂移**：功能越加越多，变成"更弱的 Dify" | 失去焦点 | §3.2 的非目标是硬约束；新增功能先过这一关 |
| **规模天花板**：Chroma + SQLite + 单机 | 上万文档后性能下降 | 已知边界（§3.1）；超出即不是目标用户，不为它做设计 |

## 附：这份方案最想说的三句话

1. **产品的真实定位是「本地私有 + 工程透明」，不是「企业级」。** 硬套后者三个问题就穿帮，诚实的定位反而更难被击穿。

2. **最大的缺口不是功能少，是「用了一个月什么都不会积累」。** 检索算法已经够好，缺的是让系统从使用中学习的那条通路。

3. **下一步性价比最高的不是大功能，是两处一行改动**：预置演示问题（让"敢说不知道"被主动看到）+ 把门控分数露给用户（让可信度被感知）。成本几乎为零，但直击首因效应和信任建立。
