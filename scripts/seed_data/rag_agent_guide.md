# RAG 与 Agent 开发基础

本手册介绍构建一个「知识库问答系统」（RAG，Retrieval-Augmented Generation）与
「文件操作 Agent」的核心原理。内容覆盖：为什么需要 RAG、混合检索、切块策略、
引用溯源、从 RAG 到 Agent、LangGraph、评估、多模态与私有化。适合第一次接触
这套技术的开发者阅读。

---

## 1. RAG 是什么，为什么需要

大语言模型（LLM）有两个先天的局限：

- **知识截止**：模型只知道训练截止日期之前的数据，新文档、公司内部资料一概不知。
- **幻觉**：遇到不知道的内容时，模型会"自信地编造"，而不是说"我不知道"。

RAG 的解决办法是：**先检索，再生成**。用户提问后，先从知识库里找出最相关的
若干段文字（检索），把它们塞进提示词（增强），再让模型基于这些文字回答（生成）。
这样模型"有据可依"，幻觉大幅下降，也能回答私有/新增内容。

RAG 的三个核心收益：

1. **回答可溯源**：答案背后有真实文档支撑，而不是模型凭空编造。
2. **知识可更新**：文档变了，重新索引即可，不用重训模型。
3. **数据可控**：知识库在本地，不把资料发给模型厂商训练。

### 什么时候不该用 RAG

RAG 不是银弹。如果问题是开放闲聊、纯推理（如数学题），或知识本来就该被模型
背下来（如常见事实），直接问模型即可，没必要检索。RAG 的适用场景是：**答案
必须来自某份具体文档**。

## 2. RAG 的四个环节

一个完整 RAG 系统分四个环节：

1. **索引（Indexing）**：把原始文档切块（chunk）→ 向量化 → 存入向量数据库。
2. **检索（Retrieval）**：把用户问题向量化 → 在向量库里找最相似的若干块。
3. **增强（Augmentation）**：把检索到的块 + 系统提示词 + 最近对话历史组装成
   一次完整的模型调用。
4. **生成（Generation）**：模型基于增强后的上下文生成带引用的答案。

这四个环节是松耦合的，每一环都可以独立替换。这也是 RAG 架构演进快的原因。

## 3. 混合检索：BM25 + 向量 + RRF

单靠一种检索方式往往不够。

- **向量检索（语义）**：把文本转成高维向量，用余弦相似度找"意思相近"的内容。
  能搜到同义改写，但搜专有名词（如 `Dockerfile`、`requirements.txt`）效果差——
  这些词的语义向量区分度低。
- **BM25（关键词）**：基于词频的经典算法，精确匹配关键词。搜专有名词很强，
  但搜不到近义词（用户说"删除"文档里写的是"移除"就搜不到）。

**混合检索**把两路都跑一遍，再用 **RRF（倒数排名融合）** 融合两个排名：

```
score = VECTOR_WEIGHT / (k + 向量排名) + BM25_WEIGHT / (k + 关键词排名)
```

RRF 的好处：它只看**排名**不看原始分数——BM25 分数和向量余弦距离范围完全不同，
无法直接相加，但排名可以。`k` 是平滑常数（常用 60），防止分母为 0。

需要权衡的是权重：有的场景纯向量就够（`BM25_WEIGHT=0`），有的场景两者各半
更好。**正确做法是拿真实问答跑一遍评估，让数据说话，而不是拍脑袋**。

### 中文分词

BM25 处理中文必须分词。中文不像英文按空格分，得先用 jieba 之类把句子切成词。
按字切分会导致"混合检索"被拆成"混/合/检/索"四个字，搜"检索"匹配不到"检"和"索"
两个孤立字，毫无意义。按词切分后 "混合检索" 是完整词，BM25 才有真正的关键词能力。

## 4. 切块策略

切块是 RAG 质量最容易被低估的一环。块太小，检索到的上下文不完整；块太大，
混入大量无关文字，稀释了模型注意力。

两个常用参数：

- **chunk_size**：每块的目标字符数（常见 300~800，中文可小些）。
- **chunk_overlap**：相邻块重叠的字符数（常见 10%~20%），避免一句话被从中间
  切断导致上下文断裂。

更好的做法是按**语义边界**切：尽量在段落、小标题、句号处切开，而不是按字符数
硬切。结构化文档（Markdown 标题、代码块、表格）切块时保留结构信息，检索时能
更准。图片/扫描件则先 OCR 成文字再切块。

### 切块的权衡

块小 → 检索精确、但上下文可能不完整；块大 → 上下文完整、但可能引入噪声。
没有唯一正确答案，取决于文档类型和问题形态。判断标准还是：**真实问题检索后，
模型能不能答对**。

## 5. 检索后的增强：提示词组装

检索到 top_k 个块之后，怎么喂给模型也很关键。

典型组装顺序：

```
[system 提示词]
  你是知识库问答助手，只根据参考文档回答，不要编造。
[历史对话]      ← 多轮追问："那第二点呢" 需要前文上下文
[参考文档 1..k]  ← 每个块带来源标注 [1] [2] ...
[当前问题]
```

几个要点：

- **系统提示词必须约束行为**：只说"只根据文档回答"不够，还要说明"没有相关信息
  就直接说没有"，否则模型会硬编。
- **历史注入要限长**：注入最近 N 条即可，否则旧对话占用上下文、还引入过时信息。
- **引用不要靠模型编**：让模型只输出序号 `[n]`，由代码把序号映射回真实文档来源。
  模型生成的"文件名/页码"不可信，代码映射才可信。

---

## 6. 引用溯源与防幻觉

回答带引用，是 RAG 区别于"裸模型"的核心卖点。

防幻觉的几道防线，从强到弱：

1. **检索不到就明说**：top_k 为空时直接回答"知识库中未找到"，不要硬答。
2. **约束提示词**：系统提示明确"只根据参考文档回答"。
3. **引用由代码映射**：模型只给 `[n]` 序号，代码把序号映射回检索来源，越界序号
   自动忽略。这样即使模型想编文件名，也映射不到真实来源。
4. **低温度**：生成用 `temperature=0.3` 这类低值，减少随机编造。

真正的防幻觉还是靠**评估**持续监控——见第 9 节。

## 7. 从 RAG 到 Agent：工具调用

RAG 只能"回答问题"。当需求变成"帮我读取文件、搜索代码、往知识库加内容"时，
就需要 **Agent（智能体）**：让模型自己决定调用哪些工具。

Agent 的工作方式叫 **ReAct**（Reason + Act）：

```
思考 → 我要读这个文件 → 调用 read_file 工具 → 看到结果 → 再思考 → 回答
```

关键点：

- **工具是显式声明给模型的**：工具名、参数、用途说明（description）要写清楚，
  模型靠 description 决定何时调用。
- **工具执行结果会喂回模型**：模型看到结果才能继续思考下一步，形成循环。
- **必须有循环上限**：防止模型无限调用工具，通常设最大步数（如 8 步）。

### 快慢路径分工

一个务实的设计：**问答走 RAG 快路径，文件操作走 Agent 慢路径**。

- 用户只问问题 → 走纯 RAG（快、带引用，一次模型调用）。
- 用户要操作文件 → 走 Agent（工具循环，多步，慢但能做实事）。

不要为了"统一"把 RAG 塞进 ReAct 循环——问答会变慢、引用变难。统一的是
记忆与能力对齐，不是底层实现。

## 8. LangGraph：节点、边、状态

手写 Agent 循环用 `while` 就能跑，但状态一多（工具结果、步数、上下文）代码就
乱。**LangGraph** 把循环结构化成"图"：

- **State**：在图中流动的数据（类比快递包裹），如消息列表、步数计数器。
- **Node**：处理 State 的函数（类比流水线工人），如"调用模型"、"执行工具"。
- **Edge**：节点之间的连线（类比岔路口），带条件判断——有工具调用就进工具节点，
  否则结束。

一个最简 Agent 图只有两个节点：

```
入口 → [call_model 调模型] → 有 tool_calls? → 有 → [call_tools 执行工具] → 回到 call_model
                                                ↓ 无
                                               结束（模型直接回答）
```

`State` 里的 `messages` 用 `Annotated[list, add_messages]` 标记，LangGraph 会自动
把每轮新增的消息追加进去，不用手动维护。

### 流式输出

让模型"打字机"式逐字输出，需要图节点用 LangChain 聊天模型（`ChatOpenAI`），
配合 `graph.stream(stream_mode=["updates", "messages"])`。messages 模式每次产出
`(AIMessageChunk, metadata)`，取 `chunk.content` 就是新 token。工具调用的中间
消息 content 为空，自动跳过——只有最终答案的文字流出来，这才是真流式。
裸 OpenAI 客户端做不到 token 级流式。

## 9. 评估：LLM-as-Judge

RAG 系统最大的坑是"感觉还行，但不知道好不好"。需要量化指标。

常用做法是 **LLM-as-Judge**：让另一个 LLM 给回答打分，四个维度：

- **Recall（召回）**：答案是否覆盖了参考文档里的关键信息。
- **Precision（精确）**：答案里的信息是否都是文档里有的（有没有编造）。
- **Faithfulness（忠实）**：答案是否忠于文档，有没有偏离。
- **Relevancy（相关）**：答案是否回答了用户的问题。

评估流程：

1. 准备一批真实问答对（问题 + 参考答案 + 所在文档）。
2. 对每个问题跑 RAG 拿回答。
3. 让 Judge LLM 按四维打分。
4. 汇总成百分比，对比不同参数（如 top_k、chunk_size、检索权重）的效果。

**评估的价值**：让"感觉好"变成"数据好"，也让参数调优有依据。这比任何代码技巧
都重要——没有评估，优化就是盲人摸象。

## 10. 多模态：OCR 与视觉模型

文档不只有文本。图片、扫描版 PDF 里的字，需要先提取出来。

- **OCR（光学字符识别）**：把图片/扫描件里的像素变成文字。本地方案如 RapidOCR，
  纯 CPU、数据不出域。扫描版 PDF 每页渲染成图再 OCR。
- **视觉模型（VLM）**：更强的方案，直接把整页图丢给多模态模型，让它"看"布局、
  输出结构化的 Markdown。本地可跑 minicpm-v 这类小模型；复杂版面（密集表格、
  双栏）本地小模型会吃力，需云端大模型或专门的版面分析。

**布局是几何信息**：OCR 只拿到文字，丢掉了"哪几行是一起的"这类空间关系，阅读
顺序可能牛头不对马嘴。要解决得让模型"看到"空间——要么捡回坐标排序，要么直接
用视觉模型看图。文本型 PDF（文字可选中的）直接用 PyMuPDF 按坐标提取即可，
根本不需要 OCR。

## 11. 上线考虑：观测、缓存、私有化

项目从 demo 到可用，还有几件事：

- **观测（Observability）**：用 Langfuse 这类工具记录每次检索、每次模型调用、
  耗时与 token。出问题能回放"它当时看到了什么、答了什么"。
- **缓存（Caching）**：重复问题直接命中缓存，不重复调模型。知识库问答高度重复，
  语义缓存（对相似问题归并）能显著省钱省时间。
- **惰性客户端**：LLM 客户端、向量库这类外部依赖，在模块 import 时不创建，首次
  调用才创建。没有密钥的环境（CI、测试）也能正常导入代码。
- **私有化**：把 embedding 和 LLM 都换成本地（Ollama），数据完全不出域，适合
  敏感场景。代价是速度和模型能力。

### 部署与 CI

代码推 GitHub 用 GitHub Actions 自动跑确定性测试（纯逻辑、不调模型），保证
每次改动不破坏核心功能。前端用 Streamlit 部署到云上，冷启动时用种子数据脚本
自动补一份演示知识库，让评审打开就能用，而不是面对空库。

---

## 结语

RAG 到 Agent 的路线图：**先让系统"答得准"（检索 + 增强），再让它"会做事"
（工具 + 循环），再用评估让它"可证明地好"（LLM-as-Judge）**。每一步都建立在
上一步之上，别跳级。
