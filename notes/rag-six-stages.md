# RAG 六环节梳理（对标截图框架 · dev-agent 现状版）

> 目标定位：**不是刷评测分数，是通过动手优化真正理解 RAG。**
> 所以每个环节都按「现状 → 该理解什么 → 可做的实验」来组织，而不是「怎么改得更好」。

## 0. 先纠一个图上的问题：漏了「在线召回」

那张图的流程是：

```
数据预处理 → 文档切分 → 文本向量化 → 入库建索引 → Rerank 精排 → 运维迭代
```

**缺了「在线召回」这一整环。** 正确的完整链路是：

```
【离线建库】数据预处理 → 文档切分 → 文本向量化 → 入库建索引
                                                      ↓
【在线检索】(用户提问) → query 向量化 → 候选召回 top_k×10 → Rerank 精排 → 取 top_k
                                                      ↓
【持续】运维迭代（评测 / 监控 / 缓存 / 增量更新）
```

为什么这一环不能省：**Rerank 排的是召回的结果**。如果召回只取 5 条，精排再准也只能从这 5 条里挑；必须先捞 50 条，精排才有发挥空间。
「多捞 → 精排」是整个 rerank 的成立前提，图上没画出来，很容易理解成「召回了再 rerank 一下」。

另外这张图还有个隐含划分值得记住：
- **前 4 步是「离线索引侧」**：文档进来时跑一次，可以慢，可以离线批处理
- **后 2 步是「在线/持续侧」**：每次提问都要跑，必须快，且要长期迭代

这两侧的优化手法完全不同（前者重质量，后者重延迟和成本）。

## 1. 数据预处理

| 项 | 内容 |
|---|---|
| **现状** | `src/cleaner.py` 已实现并接入 `parse_file()`：归一化（控制字符/全角空格/连续空行）→ 跨页页眉页脚识别去除 → 硬换行断句合并 → 垃圾块过滤。15 条单测覆盖。 |
| **关键设计** | 收口在 `parse_file()` 而不是散在各调用点，保证 Web 上传 / Agent 工具 / 脚本灌库三条路径都跑不掉。`CLEANER_ENABLED=false` 可关。 |
| **该理解什么** | 清洗**不产生新知识**，它只是让 embedding 拿到完整句子。所以它的收益高度依赖「原文有多脏」。md 本来就干净 → 收益≈0；PDF 有页眉页脚和每行硬换行 → 收益明显。 |
| **已验证** | 在建库日志里能看到清洗生效（走的是真链路），但**没测出指标变化**——因为测试语料全是 md。 |
| **待做的实验** | 造一份「脏 PDF」（带页眉页脚 + 每行硬换行 + 扫描页），开关清洗各建一次库，对比指标。**这是唯一能看到清洗真实价值的实验。** |
| **方法论提醒** | 之前清洗和分块是一起上的，导致降了不知道怪谁。**以后每次只动一个变量。** |

## 2. 文档切分

| 项 | 内容 |
|---|---|
| **现状** | 两套策略共存，开关控制：① 滑动窗口（500 字 / 重叠 50）——**当前默认**；② 标题树分块（Markdown 标题栈 + 父路径前缀）——已实现但默认关闭。 |
| **该理解什么** | 切分决定「检索的最小单位」。太小 → 语义被切断，块里没有完整答案；太大 → 一块塞进多个主题，向量被平均掉，什么都像又什么都不像。 |
| **已做的 A/B** | 标题树 vs 滑窗，**同源 14 篇 md，四项指标全降或持平**（Recall@5 0.960→0.940，Hit@1 0.840→0.800，MRR 0.887→0.873）。已回退。 |
| **最重要的结论** | MaxKB 的标题树是生产验证过的，照搬却变差——因为**它的战场是 PDF/Word**（原文无结构标题，靠 parent_chain 补上下文），md 的标题本来就在正文里，前缀是重复信息。**最佳实践有适用前提。** |
| **遗留问题** | `CHUNK_MIN_SIZE` 是死配置（定义了、import 了、从没用过）；「过短章节合并到相邻块」这个逻辑实际没实现。 |
| **待做的实验** | ① `chunk_size` 扫描 100 / 300 / 500 / 1000，看指标怎么变——直觉建立最快的一个实验；② 在 PDF 上重测标题树，验证「适用前提」这个判断。 |

## 3. 文本向量化

| 项 | 内容 |
|---|---|
| **现状** | 硅基流动 `BAAI/bge-large-zh-v1.5`，1024 维，OpenAI 兼容接口。`embed_texts()` 批量调用，文档入库不加任何前缀；查询侧走 `embed_query()`。 |
| **该理解什么** | **非对称编码**：BGE 训练时 query 和 passage 用的是不同编码方式，官方要求给 query 加一句指令前缀。所以「文档入库」和「查询」走的是两个函数，不是偷懒，是有语义的。 |
| **已做的 A/B** | 加指令前缀后 top1 余弦相似度 0.6170→0.5554（**−6.2 个点**），MRR 0.887→0.880。判断该 API 商已在服务端处理，客户端再加属重复添加。已默认关闭，保留开关。 |
| **方法论价值** | 这是一个**「文档说的对，但你的场景不适用」**的典型案例，和 MaxKB 那件事是同一类。 |
| **待做的实验** | 换模型对比：bge-m3（多语言+长文本）、text-embedding-3-small。**但要注意：换模型必须重建索引**，维度和向量空间都变了（`check_embedding_dim()` 会拦住旧库）。 |

## 4. 入库建索引

| 项 | 内容 |
|---|---|
| **现状** | Chroma PersistentClient（进程内单例），每个知识库一个 collection，`hnsw:space=cosine`。`add_chunks()` 一次 `add` 全部；id = `{文件名}_chunk{序号}`；metadata 仅 source / page / chunk_index / type / image。 |
| **该理解什么** | 向量库不是「存进去就行」，它是**近似最近邻搜索（ANN）**：HNSW 是图索引，用 `M`（每节点连边数）、`ef_construction`（建图搜索宽度）、`ef_search`（查询搜索宽度）在**召回率和速度之间做权衡**。调大 ef_search → 更准但更慢。 |
| **当前的盲区** | 代码里**没有设置任何 HNSW 参数**，全用 Chroma 默认值。这块是完全没碰过的领域。 |
| **已发现的 BUG** | **删文档只删 SQLite，不删 Chroma chunk**——文档从列表消失但内容仍被检索到。`vector_store.py` 只有删整库的 `delete_collection`，没有按 source 删 chunk 的函数。 |
| **其他短板** | ① 嵌入不分批（整个文件一次全发，大 PDF 必挂）；② 无重试（API 抖动即失败）；③ 无内容 hash 去重（同名/改名的重复文件会污染检索）。 |
| **待做的实验** | ① 调 `ef_search` 看召回率与延迟的变化曲线；② 修掉删除 BUG（这是功能错误，不是优化）。 |

## 5. Rerank 精排

| 项 | 内容 |
|---|---|
| **现状** | **完全没有。** 检索是向量 top_k 直接返回，中间没有任何精排阶段。 |
| **该理解什么（核心）** | **双塔 vs 交叉编码**：<br>· 向量检索是「双塔」——query 和 doc **分开**编码成向量，靠余弦相似度比。快，但**两者从未见过面**，丢失了词级的交互信息。<br>· Reranker 是「交叉编码」——把 query 和 doc **拼在一起**过一遍模型，直接输出相关性分数。准，但慢，只能对小候选集用。<br>这就是「先粗排捞 50 → 再精排取 5」这个架构的由来：**用便宜的方法缩小范围，用贵的方法做最终判断。** |
| **为什么要做** | 现在的失败案例（如 q05）正确答案**明明在 top5 里，只是排不到第一**。Hit@5 有 0.960 但 Hit@1 只有 0.840——这个 12% 的差距就是精排要解决的问题，**是检索链路里最明确的一块空间**。 |
| **怎么做** | ① 召回候选池扩到 `top_k × 10`；② 接 bge-reranker-v2（硅基流动有 API，零部署）；③ 精排后取 top_k。 |
| **待做的实验** | 精排前后的 Hit@1 / MRR 对比——**预期这是六个环节里指标变化最明显的一步**。 |

## 6. 运维迭代

| 项 | 内容 |
|---|---|
| **现状** | 已有：`tests/golden_set.json`（26 条：24 正样本含 2 条多跳 + 2 条负样本）、`scripts/eval_retrieval.py`（Recall@K / Hit@K / Hit@1 / MRR / 负样本最高分，支持历史对比与 JSON 存档）、语义缓存 `query_cache`（带 `vec_ver` 版本失效）、Langfuse 观测。 |
| **该理解什么** | **评测体系是 RAG 的地基，不是附属品。** 没有可信的评测，所有优化都是盲改。 |

| **待做的实验** | 把「检索评测 → 生成评测 → 历史对比」串成一条命令，每次改动一键回归。 |

## 7. 在线查询处理（追问消解 + 质量门控）

| 项 | 内容 |
|---|---|
| **现状** | 2026-09-14 落地两项：① 追问消解 `src/query_rewrite.py`；② 检索质量门控（阈值拒答）`src/answer_gate.py`。开关 `QUERY_REWRITE_ENABLED` / `RETRIEVAL_MIN_SCORE`。 |
| **① 追问消解做什么** | 检索前把「历史 + 当前问题」压成一句自包含 query；单轮提问直接跳过（不调 LLM），失败 / 空结果 / 超长一律退回原 query。 |
| **为什么这是整条链路里最划算的一处** | `pages/3` 早已把 history 取出来传给 `stream_rag_query`，但它只接进生成阶段；检索那一行吃的仍是原始字符串。**数据本来就在手，只是没接上检索。** |
| **实测（kb `83cd2d0c`，追问「那第二点呢」）** | 改写 → 「BM25 做关键词召回是怎么做的？」。精排 top5 分数：改写前 **0.8868 / 0.7999 / 0.0593 / 0.0216 / 0.0178**（前两条高分然后断崖），改写后 **0.7692 / 0.7172 / 0.6241 / 0.4919 / 0.4593**（整段落在相关区间）。 |
| **该理解什么（反直觉的一课）** | **改写后 top1 分数反而更低（0.8868 → 0.7692），但结果明显更好。** 原 query 太短太模糊，reranker 只能瞎猜，给出「高分假阳性 + 断崖」的错误分布。**只盯 top1 分数会得出完全相反的结论**——要看分数分布形态 + 内容是否真相关。另：改写解决的是"检索不到"，不解决"排序不准"。 |
| **② 质量门控做什么** | 精排分数有绝对意义（相关 0.6+ / 不相关 <0.01），据此设一道门槛：检索最高分 < 0.3 就**不把上下文交给 LLM**，改用 `NO_CONTEXT_SYSTEM_PROMPT` 如实回答。**低分上下文一律不喂——这是幻觉最直接的来源。** |
| **阈值依据（实测精排 top1）** | 可答：0.620（「混合检索是怎么做的」）、历史正样本 min 0.578；不可答：全部 ≤0.125（「你好」0.125 /「你能做什么」0.122 /「1+1」0.091 /「帮我写首诗」0.010 /「今天天气」0.001 / 已知负样本 0.0005）。取 0.3：两侧都留了余量（宁漏拒、不误拒）。 |
| **该理解什么（一个架构发现）** | 原计划单独做「意图路由」（判断该不该查库），实测发现**精排分数已经把它做到了**——闲聊 / 常识 / 越界提问的分数全部落在 0.125 以下，与可答问题相差 5 倍。**一个阈值同时覆盖「幻觉」和「不该查库」，省掉一次额外的 LLM 分类调用。** |
| **端到端实测效果** | 「今天天气怎么样？」→ 无引用，答「知识库中没有找到与天气相关的资料。另外，我无法获取实时天气信息…」；「帮我写一首关于秋天的诗」→ 先说「知识库中没有相关资料，不过写诗属于通用创作（不来自知识库）」再写诗。第二例说明：**拒答 ≠ 拒绝服务，而是明确区分"有依据"和"没依据"。** |
| **还没做（剩余）** | ③ 查询扩展 / 多查询（Multi-Query）；④ HyDE；⑤ 多跳分解。均为锦上添花。 |
| **已知局限** | 阈值是绝对分数，只能判断「结果够不够支撑回答」，判断不了「库里有但用户换了说法」（实测「文档上传大小限制是多少」= 0.039，因为库里确实没写）。另：负样本只有 2 条，真实模糊提问的中间带尚未充分采样，阈值应视为保守初值。 |

## 8. 引用与核实（产品闭环里最容易断的一环）

| 项 | 内容 |
|---|---|
| **改动前的状态** | 引用只显示「文件名 + 页码」（一行 `st.caption`）。**用户看不到原文 → 无法核实答案**，模型说的和引用到的到底对不对得上，只能自己去翻文档。 |
| **问题本质** | 引用只写文件名，等于"我说我引用了，信不信随你"。**能被核实，才叫引用。** |
| **做了什么** | ① 引用逻辑从 `rag_qa.py` 抽到 `src/citations.py`：按文档去重 + 附命中原文（`snippets`，默认截断 300 字）；② 前端展开引用即可逐句对照原文（`pages/3` 的 `_render_sources`）。 |
| **顺带解决两件事** | ① `unique_sources` 的去重循环原先在 `rag_qa.py` 里**逐字重复两遍**（工程审查记录的 P1 结构债），现收口成一个函数；② 引用逻辑原先挂在 rag_qa 上、被 langfuse 依赖绑架，`tests/test_citations.py` 在缺 langfuse 的环境**连收集都做不到**——拆出后可独立运行，测试从 3 条扩到 17 条。 |
| **实测（kb 83cd2d0c，「混合检索是怎么做的？」）** | 回退展示 4 个文档（README.md 命中 2 段被合并）；模型标了 `[n]` 时精确映射到 4 个文档 4 段，每段带原文。 |
| **该理解什么** | 引用链路有三个层次：① 让模型只给序号、不给文件名 → **防编造**；② 代码把序号映射回真实检索块 → **可追溯**；③ 给出命中原文 → **可核实**。多数项目停在 ②，但用户真正需要的是 ③。 |

## 9. 索引重建（「改完参数，老库却没变」的正解）

| 项 | 内容 |
|---|---|
| **改动前的状态** | 上传时把原始文件写进临时目录，`finally` 里**立刻删掉**。也就是说：**索引一旦建好，原始文本就没了。** |
| **问题本质（核心）** | 索引是被"冻"住的——chunk 是当时按那个 `chunk_size` 切的，向量是当时那个模型算的。**你改了配置，老文档不会自动跟着变**，它永远停留在入库那一刻的规则上。这几天改的分块 / 清洗规则，现有 4 个库其实都还是旧规则切的。 |
| **为什么不能"就地改"** | 分块变了 → chunk 边界变了 → 向量内容变了 → 只能整段重算。**重建是唯一能让老文档应用新规则的路径，而前提是原文还在。** 这也解释了 `check_embedding_dim()` 那句提示语「请用当前模型重新上传文档重建此库」——它早就点出问题，只是当时没有解法。 |
| **硬阻塞（实测发现）** | 动手前先查 `data/uploads/`：**只剩 3 张 png**。现有 4 个知识库的原文**已全部丢失**，重建无从谈起。所以这一步必须先补「保留原文」的地基，否则后面所有参数实验都只能对新库生效。 |
| **做了什么** | ① `pages/2` 上传时按库分目录保存原文（`kb_upload_dir(kb_id)`，避免同名覆盖），**不再删除**；删文档时 Chroma / SQLite / 原文三处同删；删库时连目录一起清。② 新建 `src/reindex.py`：`rebuildable_docs()` 供界面提前提示，`rebuild_kb()` 执行重建并返回 `{total, ok, chunks, missing, failed}`。③ 管理页加「♻️ 重建索引」按钮，跑完如实报告缺原文 / 失败的文档。 |
| **重建的三个设计约束** | ① **逐文档替换**，不做整库清空——单个文件失败不连累其他文档；② 缺原文的**记进 `missing` 列表，绝不动它已有的索引**（宁可留旧的，不能删了没新的）；③ 失败 = 什么都没发生（不写状态，可直接重试）。 |
| **顺带修掉的隐患** | `add_chunks()` 原顺序是「先删旧块 → 再算向量」。**embedding 一旦失败，旧内容已经被删掉了**——文档直接消失。改为**先算完向量再删旧块**，失败则原样保留。这是幂等性设计的通用原则：**破坏性操作放在不可逆步骤之后。** |
| **端到端实测** | 临时库放 3 个文档（2 个有原文 + 1 个假装的"丢原文老文档"）：结果 `{total: 3, ok: 2, chunks: 5, missing: ['早就丢了原文的老文档.md'], failed: []}`；库内 chunk = 5；缺原文那份状态保持 `processing`，旧索引未被动。 |
| **该理解什么** | 「重建索引」不是运维小功能，它是**参数实验能否落到存量数据上的前提**。没有它，你改的任何分块 / 嵌入参数都只对新上传的文档生效，老库永远测不出差异——**会让人误判"改动无效"**。 |
| **连带结论（必须知道）** | 现有 4 个库（`83cd2d0c` / `16684ef4` / `f99c2c78` / `af14d071`）**原文已丢，无法重建**，只能重新上传。从这次改动之后上传的文档才有原文留存。 |

## 10. 混合检索（BM25 真正开启）

| 项 | 内容 |
|---|---|
| **改动前的状态** | `BM25_WEIGHT=0` → `_get_bm25()` 第一行直接短路返回 `(None, [])`。**`hybrid_retriever` 这个名字与实际行为不符**：它实为纯向量单路，RRF 只收到一路排名（`rrf_score = 1/(60+rank)` 只是向量排名的单调变换，排序上等价于按向量排）。而 README 和 `pages/3` 的界面文案都写着"混合检索（BM25 + 向量）"——**文案在说一件代码没做的事**。 |
| **为什么此前测出"不如纯向量"** | 那次 A/B 大约发生在精排上线之前。**没有精排时，RRF 的顺序就是最终顺序**——BM25 一路把关键词命中但语义不相关的块混进排序，是真的会伤 Hit@1/MRR。**但精排上线后，这个前提被推翻了**（见下）。 |
| **该理解什么（本步最重要的一条）** | 有了精排之后，**RRF 的职责变了**：它不再决定"最终排名"，只决定"谁能进候选池"。因为交叉编码会把池子里**每一条**重新打分。→ 于是 **BM25 从"可能污染排序的风险项"变成了"纯召回增量"**：它只能把新块塞进池子，塞进去的垃圾会被精排打低分自然沉底。**加一路召回的风险，取决于下游有没有一道统一的重打分关卡。** |
| **顺带发现的问题（代价漏洞）** | 融合结果是**不截断**地整包送进精排的。所以"多开一路召回"等于"顺手把精排账单抬高一截"（精排按文档条数计费）。实测 BM25 每问平均送来 41.8 条，池子从 50 涨到约 65，精排批次 2→3（+50%）。 |
| **做了什么** | ① `BM25_WEIGHT` / `VECTOR_WEIGHT` **改成 env 可配**（项目里所有开关都是这么做的，只有这两个是硬编码——这正是它当年 A/B 完就再也没法复测的原因）；② `_tokenize` 加**停用词 + 标点过滤**（jieba 会把"，""？"也切成 token；孤立的 `_` 也要丢）；③ BM25 **零分词块不入池**；④ RRF 融合后**截断回候选池大小**；⑤ 评测存档新增 `bm25_weight` / `vector_weight` 字段（否则两次结果没法归因）；⑥ `.env.example` 补上检索侧全部开关（此前只能翻代码发现）。 |
| **实测（kb `83cd2d0c` / 26 条 / 精排开，只切 BM25_WEIGHT）** | Recall@5、Hit@5、Hit@1、MRR **两组完全一致**，都是 `1.000 / 1.000 / 0.917 / 0.958`；负样本最高分 0.0005 不变。候选池 **50 → 50**，精排批次 **2 → 2**（截断生效，精排账单零增加）。BM25 净贡献：每问平均 **15.1 条**向量 top50 未覆盖的 chunk（**25/26 道题都有**）。存档 `data/eval_history/retrieval_eval_20260914_184307.json`。 |
| **代价（实测，108 chunk 库）** | 精排 API 零增加。**延迟**：其余每一问 **+30~60 ms**；**冷启动第一问 +527 ms**（2990 → 3517 ms，≈ jieba 词典初始化 0.54 s），且**每次文档增删后索引缓存失效会再吃一次构建**（108 chunk 全量分词 96 ms + 建索引 3 ms）。缓存键是"chunk 总数"，所以这两项都随库大小线性增长——**库到 1000 chunk 量级时，每次增删后的首次检索要多等约 1 秒**。这是"开了它到底贵不贵"的真答案：贵不在 API，在**惰性构建**。 |
| **结论：为什么还开** | 本测试集**测不出差异**，但这不是"没用"，是"没压到它的强项"——26 条全是自然语言问句，而 BM25 补的是**词面精确匹配**（专有名词、代码标识符、基金代码在向量空间里没有语义邻居）。加上代价为零、排序无风险，开它的收益是**能力覆盖**与**文案诚实**，不是分数。**别把"测不出差异"当成"没有价值"**——先问这个测试集有没有覆盖到那个能力。 |
| **🔬 副产品：尺子本身有噪声（差点误判）** | 中途我量到"BM25 开后 top2~5 精排分之和 +2.6%"，差点当成收益写进结论。于是先去验证尺子：**同一批输入连调三次精排 API，分数最大差 ±0.0108（50 条里 30 条差异 >1e-4），但前 5 名索引三次完全相同。** → 那个 +2.6% 落在抖动内，**作废**。同时排查了上游：查询向量三次嵌入**逐位相同**、Chroma 检索三次**顺序完全一致**——抖动只来自精排批量推理本身。**教训：分数绝对值不是精确量，只有排名类指标（Recall / Hit@K / MRR）可作判据；比较分数差值时先确认它大于噪声底。** |
| **与门控阈值的关系** | 门控阈值 0.3 建立在精排分数上，而抖动只有 ±0.01、两侧间距是 0.125 ↔ 0.578（**约 4.6 倍**）——余量足够，阈值不需要为抖动调整。 |

## 11. Word 表格解析（静默丢数据）

矛盾点：整条链路上大家都在盯"检索准不准"，但**上游把内容吞掉了，下游再准也是白准**。
这一节记的不是优化，是一个**内容正确性 bug**——它比"检索差一点"严重得多。

| 项 | 内容 |
|---|---|
| **改动前的状态** | `parse_docx()` 只读 `doc.paragraphs`，`doc.tables` **完全没碰**。实测（2×2 + 3×3 两张表）：**7 个关键值全部丢失，13 个单元格内容一个不剩**，返回块长度只剩 51 字符。 |
| **为什么是这个写法（根因）** | `python-docx` 的 `doc.paragraphs` **只返回 body 直属的 `<w:p>`**；表格里的段落嵌套在 `<w:tbl>` 内，**不在其中**。`doc.paragraphs` 和 `doc.tables` 是两套独立收集，互不包含。 |
| **为什么这是最糟的一类 bug** | 它是**静默**的：不报错、文档照样标 `ready`、用户毫无感知。而 Word 里信息密度最高的恰恰是表格（参数表、对比矩阵、规格表）——恰恰是用户最想问的东西。**报错能被发现，静默丢数据不能。** 缺功能用户能感知，静默丢数据用户永远不知道。 |
| **该理解什么（本步核心）** | **为什么要序列化，而不是"把表格文字拼进去"就行。** 检索单元是 chunk（500 字 + 50 重叠），**不是整张表**。表格一旦被切开，表头大概率落不到同一块里——命中的是 `| 025490 | 12.5% |` 这一行，模型既不知道 025490 是基金代码，也不知道 12.5% 是年化收益。更糟的是 `\|` 分隔符本身不携带语义，会稀释嵌入向量。→ 所以选择**行式「列名：值」**：`- 基金代码：025490；年化收益：12.5%`，**任意一行单独拿出来都自包含**。这是"检索单元是 chunk 而非整表"这个前提的直接推论。 |
| **两个反向约束（都不是随手写的）** | ① **顺序必须按 body 真实阅读顺序迭代**（`doc.element.body` 的 XML 子节点）。分别读 `doc.paragraphs` 和 `doc.tables` 会各自有序、合并后顺序丢失——表格被整体挪到文末，上下文就断了。python-docx 没内置这个迭代器（官方 FAQ 给的就是这个 recipe）。<br>② **每行前缀 `- ` 是与清洗层的隐式契约**。`merge_broken_lines` 会把"不以句末标点结尾"的行与下一行合并，而单元格值常以 `12.5%` / `3.11` 结尾——**行结构必然被吞掉**。`-` 在 `_NO_MERGE_PREFIX` 里，天然免疫。同理块间必须用**空行**分隔，单换行会让"不以标点结尾的段落"与下一段粘成一行（顺带修掉了老问题：`一、安装步骤` 后面那句会被粘上去）。 |
| **合并单元格的两处不对称处理** | · **横向合并**：同一个 `<w:tc>` 会在多个列位重复出现，必须按 `_tc` 身份**去重**——否则同一个值会挂到两个列名下（`配置项：本节无配置；值：本节无配置`，是错的）。<br>· **纵向合并**：python-docx 对续行**重复返回起始格内容**，这里**故意不去重**——重复反而正确：让组内每一行都补全自己所属的分组，避免出现 `- 维度：1024` 这种不知道属于谁的"孤儿行"。 |
| **降级策略** | 空单元格 / 全空行 → 跳过（不产生 `列名：` 空配对）；表头单元格为空 → 退回「第 N 列」保证值不丢；单行表 → 没有列名可配，按原样输出；整表无内容 → 不产生块；单元格内多段落 → 压平（换行会打断「列名：值」配对）。 |
| **测试** | 新增 `tests/test_parser_docx.py` **23 条**（`parser.py` 此前**零测试**）。其中最关键的两条：① **回归测试**直接断言表格内容不丢（把 bug 钉死）；② **端到端**跑真实 `parse_file`（含清洗层）后断言 `12.5%` 结尾的行**没有**被粘成一行、表格后的段落也没被吸进表格。全量 **213 passed**。 |
| **PDF 是另一回事（实测澄清）** | 之前把 PDF 标为"同类待查"，本轮实测说清了：**PDF 里内容一个不少，丢的是结构**。一张 3×3 表格解析出来是<br>`基金代码年化收益风险等级025490` / `12.5%中高270042` / `8.3%中`<br>——表头三字段被压成一行，`025490` 被吸到第一行末尾，第二行又混进上一行的 `12.5%中高`。根因是 **PDF 文本层里没有表格结构、只有坐标**。→ 与 docx **不是同一量级**：docx 是"有现成结构可读，只是没读"，PDF 是"要从坐标里无中生有地推断结构"（行/列聚类）。类比：**一个是你把书架上那本书漏掉了，一个是你手上只有一堆散页。** |

## 行动顺序建议（按「理解价值」而非「指标收益」）

| 顺序 | 环节 | 为什么排这里 |
|---|---|---|
| **1** | **Rerank 精排 + 候选池扩大** | 理解价值最高（双塔 vs 交叉编码是 RAG 最核心的架构权衡），且**指标变化最明显**，能立刻建立正反馈。不需要新模型部署。 |
| **2** | **运维迭代（评测串成流水线）** | 有了精排这组对比数据，正好把「一键回归」建起来，后面每步都受益。 |
| **3** | **入库建索引** | 修删除 BUG（功能错误，面试会问）+ 分批重试；再玩 HNSW 参数，进入完全没碰过的 ANN 世界。 |
| **4** | **文档切分（换 PDF 重测）** | 用 PDF 验证「标题树/清洗的适用前提」这个判断，把前面那两课闭环。 |
| **5** | **数据预处理（PDF 实验）** | 跟 4 一起做，同一份脏 PDF 就能同时验证清洗和分块。 |
| **6** | **文本向量化（换模型）** | 放最后：成本最高（要重建所有索引），且当前模型够用，属于「知道了就行」。 |

## 附：三个贯穿始终的方法论

1. **一次只动一个变量。** 清洗+分块一起上，结果降了却无法归因，白做一轮。
2. **先验证尺子，再验证改动。** 指标饱和时，所有 A/B 都是幻觉。
3. **最佳实践必须放回自己场景重测。** MaxKB 标题树、BGE 指令前缀，两个都是「文档说对、我们这儿不成立」。
