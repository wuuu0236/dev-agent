# RAG 六环节梳理（对标截图框架 · dev-agent 现状版）

> 目标定位：**不是刷评测分数，是通过动手优化真正理解 RAG。**
> 所以每个环节都按「现状 → 该理解什么 → 可做的实验」来组织，而不是「怎么改得更好」。

## 0. 先纠一个图上的问题：漏了「在线召回」

那张图的流程是：

```
数据预处理 → 文档切分 → 文本向量化 → 入库建索引 → Rerank 精排 → 运维迭代
```

**缺了「在线召回」这一整环。** 正确的完整链路是：

```
【离线建库】数据预处理 → 文档切分 → 文本向量化 → 入库建索引
                                                      ↓
【在线检索】(用户提问) → query 向量化 → 候选召回 top_k×10 → Rerank 精排 → 取 top_k
                                                      ↓
【持续】运维迭代（评测 / 监控 / 缓存 / 增量更新）
```

为什么这一环不能省：**Rerank 排的是召回的结果**。如果召回只取 5 条，精排再准也只能从这 5 条里挑；必须先捞 50 条，精排才有发挥空间。
「多捞 → 精排」是整个 rerank 的成立前提，图上没画出来，很容易理解成「召回了再 rerank 一下」。

另外这张图还有个隐含划分值得记住：
- **前 4 步是「离线索引侧」**：文档进来时跑一次，可以慢，可以离线批处理
- **后 2 步是「在线/持续侧」**：每次提问都要跑，必须快，且要长期迭代

这两侧的优化手法完全不同（前者重质量，后者重延迟和成本）。

## 1. 数据预处理

| 项 | 内容 |
|---|---|
| **现状** | `src/cleaner.py` 已实现并接入 `parse_file()`：归一化（控制字符/全角空格/连续空行）→ 跨页页眉页脚识别去除 → 硬换行断句合并 → 垃圾块过滤。15 条单测覆盖。 |
| **关键设计** | 收口在 `parse_file()` 而不是散在各调用点，保证 Web 上传 / Agent 工具 / 脚本灌库三条路径都跑不掉。`CLEANER_ENABLED=false` 可关。 |
| **该理解什么** | 清洗**不产生新知识**，它只是让 embedding 拿到完整句子。所以它的收益高度依赖「原文有多脏」。md 本来就干净 → 收益≈0；PDF 有页眉页脚和每行硬换行 → 收益明显。 |
| **已验证** | 在建库日志里能看到清洗生效（走的是真链路），但**没测出指标变化**——因为测试语料全是 md。 |
| **待做的实验** | 造一份「脏 PDF」（带页眉页脚 + 每行硬换行 + 扫描页），开关清洗各建一次库，对比指标。**这是唯一能看到清洗真实价值的实验。** |
| **方法论提醒** | 之前清洗和分块是一起上的，导致降了不知道怪谁。**以后每次只动一个变量。** |

## 2. 文档切分

| 项 | 内容 |
|---|---|
| **现状** | 两套策略共存，开关控制：① 滑动窗口（500 字 / 重叠 50）——**当前默认**；② 标题树分块（Markdown 标题栈 + 父路径前缀）——已实现但默认关闭。 |
| **该理解什么** | 切分决定「检索的最小单位」。太小 → 语义被切断，块里没有完整答案；太大 → 一块塞进多个主题，向量被平均掉，什么都像又什么都不像。 |
| **已做的 A/B** | 标题树 vs 滑窗，**同源 14 篇 md，四项指标全降或持平**（Recall@5 0.960→0.940，Hit@1 0.840→0.800，MRR 0.887→0.873）。已回退。 |
| **最重要的结论** | MaxKB 的标题树是生产验证过的，照搬却变差——因为**它的战场是 PDF/Word**（原文无结构标题，靠 parent_chain 补上下文），md 的标题本来就在正文里，前缀是重复信息。**最佳实践有适用前提。** |
| **遗留问题** | `CHUNK_MIN_SIZE` 是死配置（定义了、import 了、从没用过）；「过短章节合并到相邻块」这个逻辑实际没实现。 |
| **待做的实验** | ① `chunk_size` 扫描 100 / 300 / 500 / 1000，看指标怎么变——直觉建立最快的一个实验；② 在 PDF 上重测标题树，验证「适用前提」这个判断。 |

## 3. 文本向量化

| 项 | 内容 |
|---|---|
| **现状** | 硅基流动 `BAAI/bge-large-zh-v1.5`，1024 维，OpenAI 兼容接口。`embed_texts()` 批量调用，文档入库不加任何前缀；查询侧走 `embed_query()`。 |
| **该理解什么** | **非对称编码**：BGE 训练时 query 和 passage 用的是不同编码方式，官方要求给 query 加一句指令前缀。所以「文档入库」和「查询」走的是两个函数，不是偷懒，是有语义的。 |
| **已做的 A/B** | 加指令前缀后 top1 余弦相似度 0.6170→0.5554（**−6.2 个点**），MRR 0.887→0.880。判断该 API 商已在服务端处理，客户端再加属重复添加。已默认关闭，保留开关。 |
| **方法论价值** | 这是一个**「文档说的对，但你的场景不适用」**的典型案例，和 MaxKB 那件事是同一类。 |
| **待做的实验** | 换模型对比：bge-m3（多语言+长文本）、text-embedding-3-small。**但要注意：换模型必须重建索引**，维度和向量空间都变了（`check_embedding_dim()` 会拦住旧库）。 |

## 4. 入库建索引

| 项 | 内容 |
|---|---|
| **现状** | Chroma PersistentClient（进程内单例），每个知识库一个 collection，`hnsw:space=cosine`。`add_chunks()` 一次 `add` 全部；id = `{文件名}_chunk{序号}`；metadata 仅 source / page / chunk_index / type / image。 |
| **该理解什么** | 向量库不是「存进去就行」，它是**近似最近邻搜索（ANN）**：HNSW 是图索引，用 `M`（每节点连边数）、`ef_construction`（建图搜索宽度）、`ef_search`（查询搜索宽度）在**召回率和速度之间做权衡**。调大 ef_search → 更准但更慢。 |
| **当前的盲区** | 代码里**没有设置任何 HNSW 参数**，全用 Chroma 默认值。这块是完全没碰过的领域。 |
| **已发现的 BUG** | **删文档只删 SQLite，不删 Chroma chunk**——文档从列表消失但内容仍被检索到。`vector_store.py` 只有删整库的 `delete_collection`，没有按 source 删 chunk 的函数。 |
| **其他短板** | ① 嵌入不分批（整个文件一次全发，大 PDF 必挂）；② 无重试（API 抖动即失败）；③ 无内容 hash 去重（同名/改名的重复文件会污染检索）。 |
| **待做的实验** | ① 调 `ef_search` 看召回率与延迟的变化曲线；② 修掉删除 BUG（这是功能错误，不是优化）。 |

## 5. Rerank 精排

| 项 | 内容 |
|---|---|
| **现状** | **完全没有。** 检索是向量 top_k 直接返回，中间没有任何精排阶段。 |
| **该理解什么（核心）** | **双塔 vs 交叉编码**：<br>· 向量检索是「双塔」——query 和 doc **分开**编码成向量，靠余弦相似度比。快，但**两者从未见过面**，丢失了词级的交互信息。<br>· Reranker 是「交叉编码」——把 query 和 doc **拼在一起**过一遍模型，直接输出相关性分数。准，但慢，只能对小候选集用。<br>这就是「先粗排捞 50 → 再精排取 5」这个架构的由来：**用便宜的方法缩小范围，用贵的方法做最终判断。** |
| **为什么要做** | 现在的失败案例（如 q05）正确答案**明明在 top5 里，只是排不到第一**。Hit@5 有 0.960 但 Hit@1 只有 0.840——这个 12% 的差距就是精排要解决的问题，**是检索链路里最明确的一块空间**。 |
| **怎么做** | ① 召回候选池扩到 `top_k × 10`；② 接 bge-reranker-v2（硅基流动有 API，零部署）；③ 精排后取 top_k。 |
| **待做的实验** | 精排前后的 Hit@1 / MRR 对比——**预期这是六个环节里指标变化最明显的一步**。 |

## 6. 运维迭代

| 项 | 内容 |
|---|---|
| **现状** | 已有：`tests/golden_set.json`（26 条：24 正样本含 2 条多跳 + 2 条负样本）、`scripts/eval_retrieval.py`（Recall@K / Hit@K / Hit@1 / MRR / 负样本最高分，支持历史对比与 JSON 存档）、语义缓存 `query_cache`（带 `vec_ver` 版本失效）、Langfuse 观测。 |
| **该理解什么** | **评测体系是 RAG 的地基，不是附属品。** 没有可信的评测，所有优化都是盲改。 |
| **已踩的坑（最值钱的一课）** | 最初 A/B 两组数字**完全一样**——不是改动无效，是原库只有 18 个 chunk，`top_k=5` 捞了全库 28%，**Recall@5 恒等于 1.0，尺子失灵了**。建了 108 chunk 的语料才恢复区分度。**任何优化开始前，先验证你的尺子能测出差异。** |
| **待补的能力** | ① 生成侧评测（RAGAS 四指标，项目里已有 `src/evaluation_ragas.py`，但没跟检索评测串成一条流水线）；② 数据更新/增量索引（现在改文档要重建整库）；③ 成本与延迟监控（token 消耗、P95 延迟）。 |
| **待做的实验** | 把「检索评测 → 生成评测 → 历史对比」串成一条命令，每次改动一键回归。 |

## 7. 在线查询处理（追问消解）

| 项 | 内容 |
|---|---|
| **现状** | 2026-09-14 落地「追问消解」：`src/query_rewrite.py`。检索前把「历史 + 当前问题」压成一句自包含 query；单轮提问直接跳过（不调 LLM），失败 / 空结果 / 超长一律退回原 query。开关 `QUERY_REWRITE_ENABLED`。 |
| **为什么这是整条链路里最划算的一处** | `pages/3` 早已把 history 取出来传给 `stream_rag_query`，但它只接进生成阶段；检索那一行吃的仍是原始字符串。**数据本来就在手，只是没接上检索。** |
| **实测（kb `83cd2d0c`，追问「那第二点呢」）** | 改写 → 「BM25 做关键词召回是怎么做的？」。精排 top5 分数：改写前 **0.8868 / 0.7999 / 0.0593 / 0.0216 / 0.0178**（前两条高分然后断崖），改写后 **0.7692 / 0.7172 / 0.6241 / 0.4919 / 0.4593**（整段落在相关区间）。 |
| **该理解什么（反直觉的一课）** | **改写后 top1 分数反而更低（0.8868 → 0.7692），但结果明显更好。** 原 query 太短太模糊，reranker 只能瞎猜，给出「高分假阳性 + 断崖」的错误分布。**只盯 top1 分数会得出完全相反的结论**——要看分数分布形态 + 内容是否真相关。 |
| **还没做（本环节剩余 4 项）** | ① 检索层阈值拒答（建在 rerank 分数上——`config.py` 早论证过、代码没实现）；② 意图路由（问「你好」不该塞 top5 进 prompt）；③ 查询扩展 / 多查询；④ HyDE。建议顺序 ② → ① → ③④。 |

## 行动顺序建议（按「理解价值」而非「指标收益」）

| 顺序 | 环节 | 为什么排这里 |
|---|---|---|
| **1** | **Rerank 精排 + 候选池扩大** | 理解价值最高（双塔 vs 交叉编码是 RAG 最核心的架构权衡），且**指标变化最明显**，能立刻建立正反馈。不需要新模型部署。 |
| **2** | **运维迭代（评测串成流水线）** | 有了精排这组对比数据，正好把「一键回归」建起来，后面每步都受益。 |
| **3** | **入库建索引** | 修删除 BUG（功能错误，面试会问）+ 分批重试；再玩 HNSW 参数，进入完全没碰过的 ANN 世界。 |
| **4** | **文档切分（换 PDF 重测）** | 用 PDF 验证「标题树/清洗的适用前提」这个判断，把前面那两课闭环。 |
| **5** | **数据预处理（PDF 实验）** | 跟 4 一起做，同一份脏 PDF 就能同时验证清洗和分块。 |
| **6** | **文本向量化（换模型）** | 放最后：成本最高（要重建所有索引），且当前模型够用，属于「知道了就行」。 |

## 附：三个贯穿始终的方法论

1. **一次只动一个变量。** 清洗+分块一起上，结果降了却无法归因，白做一轮。
2. **先验证尺子，再验证改动。** 指标饱和时，所有 A/B 都是幻觉。
3. **最佳实践必须放回自己场景重测。** MaxKB 标题树、BGE 指令前缀，两个都是「文档说对、我们这儿不成立」。
